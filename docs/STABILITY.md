# Corrent Stability Roadmap ("stable as steel")

Drafted 2026-10-08 from the code at `2801a8d`. Every finding cites a file and line. Findings marked *suspected* have to be confirmed by a failing test before they are fixed. Opus agents drafted and reviewed this plan, because Fable was out of usage credits (CLAUDE.md asks for Fable). A Fable review is still welcome when Fable is available.

## Goal and scope

The app must:
- never lose user data,
- never crash or hang,
- never corrupt downloads,
- recover from every external failure,
- stay fast through months of uptime.

The feature roadmap (`docs/ROADMAP.md`) is finished. This roadmap adds no features. It hardens what exists and adds the tests that prove the hardening works.

**Legend**
- **[O]**: needs the owner (pushing so CI runs, admin rights, real Linux/macOS, sleep/hibernate, signing, upstream PRs).
- **[V]**: a CORRENT PATCH in `vendor/librqbit` (record it in `CORRENT-PATCH.md` and `docs/upstream/`).
- **[U]**: a candidate for an upstream PR.
- **[new-vendor]**: needs another crate vendored. Avoid this where a Corrent-side check is enough.

All local test runs use `--portable` and scratch folders. UI checks use the debug hooks and `PrintWindow`, never real input. Fault scripts that change permissions, attributes or locks (`icacls`, `attrib`, `fault/*.ps1`) act only on paths under the scratch folder and `target/debug/corrent-data`.

**Budgets (used everywhere in this doc):** actor tick p99 < 20 ms. Frame p99 < 16 ms, where frame time is the CPU time of one kittest `run()` (headless).

## Workstream F — Failure inventory

### F-A. Awaits and blocking calls that can hang

| Item | What / why | How | Acceptance |
|---|---|---|---|
| F1 Blocking fs on the actor | Each `tick()` runs synchronous I/O on a tokio worker inside the actor loop: `free_space()` every 20 ticks (`actor.rs:1407`, `:2473`), `watch.poll()` `read_dir`/`read` every 6 ticks (`actor.rs:1410`, `engine/automation.rs:27–39`), and `store.maybe_save()` with `sync_all` (`store.rs:344–370`). Forced saves run on the actor after every add or delete completion: `store.maybe_save(true)` at `actor.rs:539`, `:1045`, `:1265`, `:1310`, `:1369`. A 500-torrent batch add means 500 full pretty-JSON rewrites plus fsyncs on the actor. `rss.json` saves (`rss/mod.rs:435–442`, `write_atomic`) also run on the actor. With an offline SMB share, a sleeping USB disk or a slow HDD, the actor stalls. Snapshots stop and the UI shows "engine isn't responding" (`app/mod.rs:573`). | **Part 1 (S1, lands with D4):** move store and `rss.json` saves to a dedicated `corrent-writer` thread. The actor sends a serialized `Vec<u8>` and gets the result back. Saves are coalesced (newest wins), so `maybe_save(true)` becomes "save soon", not "save now", and a batch add costs one or two writes. Shutdown does a final synchronous flush. **Part 2 (S3):** move free-space and watch polling into `spawn_blocking` tasks that report through `Internal` messages, at most one in flight per kind. | A 500-torrent batch add does ≤ 5 store writes. A fault test with a 30 s delay injected on `watch`/`free_space`/store paths keeps snapshot generations advancing (tick p99 < 20 ms). |
| F2 Blocking I/O on the UI thread | Breaks the invariant "the UI thread never blocks on I/O": `save_settings` → `write_atomic` + fsync (`app/mod.rs:708`, `config.rs:633`); clipboard read when the magnet dialog opens (`app/dialogs.rs:162`; can block on X11/Wayland); `dnd.rs:61–62` metadata/read of a dropped path. | Settings saves go to the same writer thread, with an in-memory "pending" copy so the UI keeps the latest. Clipboard reads go to a short-lived thread with a 500 ms deadline (pre-fill only when the read arrives in time). Dropped-file reads go to `spawn_blocking`. | Kittest test with a 5 s save delay injected: frames keep rendering (frame p99 < 16 ms). |
| F3 Engine start: no deadline, misleading port fallback | `session::create` (`engine/session.rs:98–123`) awaits `ipfilter::prepare` (HTTP, 30 s timeout per list) and then `Session::new_with_opts`, which has no timeout. The actor runs this inline (`actor.rs:276–307`, `:631`, `:731`), so no commands are handled meanwhile. Also, when the fixed port is configured, `create` retries on a random port after *any* error (`engine/session.rs:106–119`) and tells the user "Port N is unavailable". A corrupt `session.json` is then blamed on the port, and the retry fails the same way. | Wrap each attempt in `timeout(60 s)`. Use the cached IP-filter list right away and refresh it in the background (it applies at the next restart). Publish `EngineState::Starting{phase}` so the UI can show what is slow. **Port fallback (S2, with D6a):** retry on a random port only when the error chain contains an address-in-use / access-denied bind error; any other error is reported as itself and goes to D6a recovery. | A fault test with a blackholed list URL: the engine is Running in < 5 s using the cache. A test with a garbage `session.json` and a fixed port: the error names the session database, not the port. |
| F4 librqbit HTTP client has no timeout and no size cap **[V]** | The session's reqwest client (`vendor/librqbit/src/session.rs:704–720`) has no timeout. `torrent_from_url` (`session.rs:155–171`) calls `response.bytes()` with no limit. This path is used for URL adds from RSS, the Web API `urls=` field and the add dialog. HTTP tracker responses have the same problem (`librqbit-tracker-comms tracker_comms.rs:297`, not vendored). | Patch the client builder in `session.rs` with `.timeout(60s).connect_timeout(15s)`. Read the body with a 32 MiB cap by streaming chunks, like `rss/feed.rs:111`. For trackers, the client timeout bounds hangs. The size cap needs [new-vendor] tracker-comms or an upstream fix [U]; the S12 soak measures the risk first. | A test server that trickles 1 byte/s or sends 1 GiB: the add fails within 60 s with a clear error and memory stays flat. |
| F5 Stream writes to a stalled player | `engine/stream.rs:548–552` waits on `write_all` forever. A player that stops reading keeps one of the 3 permits (`MAX_STREAMS`, `stream.rs:362`) until the user presses Stop. | Wrap each piece write in `timeout(60 s)`. Reading stays untimed, because buffering on missing pieces is legitimate and Stop already covers it. | A test client that stops reading frees its permit within 60 s. |
| F6 Web API without HTTP timeouts (low priority) | `axum::serve` (`webapi/mod.rs:105`) has no header or idle timeout, so slow-loris clients can exhaust file handles. Low priority: the API is opt-in and listens on 127.0.0.1 unless LAN access is enabled (`webapi/mod.rs:4`). | Add `tower_http::timeout` (or hyper-util header-read timeout: 10 s header, 120 s body) and a cap of 64 concurrent connections. | A test that opens 500 idle sockets: the API still answers and the process handle count is bounded. |
| F7 IPC server | One thread per client with no read timeout (`single_instance.rs:121–134`). A client that never sends leaks a thread. `incoming()` errors `continue` immediately (`:122`), so a deleted socket file turns into a hot loop. | Set a 2 s read timeout on the stream (interprocess `set_recv_timeout`, or a deadline thread). Back off 250 ms after accept errors, like `stream.rs:385`. Cap live clients at 8. | A unit test with a silent client: its thread exits within 3 s. Simulated accept errors use < 1% CPU. |
| F8 Notifications spawn a thread each | `app/window.rs:98` spawns one OS thread per notification. A batch of 500 RSS completions means 500 threads, and on Linux each can block on D-Bus when no daemon runs. | One `corrent-notify` worker with a bounded queue (32). Coalesce extra items into "N downloads finished". | 1,000 completions spawn ≤ 1 thread. |
| F9 Lock held around a process spawn (trivial) | `util::local_offset_secs` holds a std `Mutex` while it runs `date +%z` (`util.rs:202–219`, Unix). Trivial: the lock is taken for the spawn at most once per 10 min (`util.rs:199–203`), Unix only. | Compute outside the lock and store the result. | Code review plus a unit test. |
| F10 Fire-and-forget engine calls | Pause/unpause tasks (`actor.rs:1163`, `:2059`, `:2084`) and inline `sess.pause/unpause/update_only_files` (`actor.rs:554`, `:839`, `:857`) have no deadline. A librqbit lock stall there freezes the actor loop. | Run the inline calls with `timeout(10 s)` and log on timeout. Record the operation name in the actor's breadcrumb (O6). | A fault-injected 30 s delay in `pause` leaves the actor responsive. |

### F-B. Unbounded growth over weeks of uptime

| Item | What / why | How | Acceptance |
|---|---|---|---|
| F11 Channels | The command channel is unbounded (`engine/mod.rs:273`), so is `internal_tx` (`actor.rs:167`), and the events channel is an unbounded `std::mpsc` drained only when the UI runs `update` (`app/mod.rs:757`). While hidden in the tray, the UI may not run (*suspected*, verify). Web API clients can queue `Add` commands carrying up to 32 MiB each (`webapi/mod.rs:128`). | Commands: a bounded `mpsc(1024)`. UI sends use `try_send` and show a "busy" toast when full. The Web API answers 503 when full. Events: drained by a 1 s timer even when hidden (`request_repaint_after` works for hidden viewports on Windows: verify), or a bounded channel that drops the oldest toast. | Soak (S12): channel depth stays < 100 at p99. A test sending 10k adds: memory stays bounded and a 503 is returned. |
| F12 `rss_failures` map (trivial) | `rss_failures` is never pruned (`actor.rs:152`, `:1231`). It grows only on failed RSS adds. The other actor maps are already pruned: `stream_haves` on every publish (`actor.rs:1876`), `category_limits` in `apply_torrent_limits` (`actor.rs:1099–1100`), `failed` on delete and on a successful retry (`actor.rs:535`, `:1339`). | Cap it together with `rss.downloaded` (drop keys that are no longer in it). Add a debug-only `Actor::sizes()` that reports every map length to the soak sampler. | Unit test. Soak: every map length stays ≤ (torrents + constant) over 24 h. |
| F13 librqbit peer map **[V][U]** | Every address seen through DHT, trackers or PEX stays in `PeerStates::states` (`torrent_state/live/peers/mod.rs:41–55`). Entries are removed only in `drop_peer` (`live/mod.rs:1315`, `:1406`). A popular torrent, or a malicious PEX flooder, grows the map without limit. | First measure it in the soak. Then cap at 2,000 per torrent, evicting dead or backed-off peers by oldest attempt. | A malicious-peer test (E3) sending 100k PEX addresses keeps the map ≤ cap. 72 h soak: flat. |
| F14 Web API sessions | `sids` are pruned only when a new login arrives (`webapi/auth.rs:78–84`). | Prune in `check()` as well and cap at 256 (evict the oldest). | Unit test. |
| F15 Disk growth | `corrent.log` is rotated only at startup when > 10 MB (`main.rs:183–185`). `store.json.bad-<ts>`, `settings.toml.bad-<ts>`, `pre-restore-<ts>/` (`backup.rs:139`) and migration backups are never pruned. | Size-based rotation while running (O1). A retention policy at startup through `util::keep_generations` (D4): keep the 3 newest of each kind, plus anything younger than 30 days. | A unit test on a temp dir with 20 old artifacts leaves exactly the expected ones. |
| F16 O(n) full rewrites | Each store save serializes the whole store as pretty JSON (`store.rs:352`), and a save is forced after every add or delete completion (`actor.rs:539`, `:1045`, `:1265`, `:1310`, `:1369`), so a batch of n adds costs O(n²) bytes written. `rss.json` is rewritten whole on each change (`rss/mod.rs:435–442`). librqbit rewrites the whole `session.json` on every add or state change (`session_persistence/json.rs:88–114`). With 10k torrents this costs CPU and fsync time on every change. | Coalescing on the writer thread (F1 part 1) removes the per-add forced saves. Measure in L4. If a store save still takes > 50 ms at 10k, use compact JSON, which shrinks it about 2×. Leave librqbit's format alone (session.json format compatibility), but debounce flushes in a patch only if L4 shows a problem. | L4 numbers recorded in `docs/PERFORMANCE.md`, including bytes written for a 500-torrent batch add. |

## Workstream D — Data durability

| Item | What / why | How | Acceptance |
|---|---|---|---|

## Workstream I — Fault injection

### Harness (three layers)

1. **In-process fs faults (Claude, every OS).** Add `src/util/faults.rs`, compiled only with `cfg(any(test, feature = "fault-injection"))`. It is a global table of rules `{op: Write|Rename|Read|Fsync|ReadDir|FreeSpace, path_glob, error: DiskFull|Permission|Locked|Eio|Delay(ms), count}`, consulted by `write_atomic`, the store writer, `free_space`, the watch poll and `move_files`. A release test (R7) asserts the symbol `faults::inject` is absent from the release binary.
2. **Engine storage faults [V].** Add a `FaultyStorage` middleware next to `vendor/librqbit/src/storage/middleware/{slow,timing}.rs`. It wraps `FilesystemStorage` and fails `pwrite`/`pread`/`ensure_file_length` according to the same rules (ENOSPC after N bytes, EACCES, EIO, delay). It is passed through a test-only `AddRequest.storage_factory`. Data-path disk-full and slow disks become deterministic tests.
3. **Network faults (Claude).** Add a tokio TCP proxy in `tests/support/netproxy.rs` between leecher and seeder, using `initial_peers` pointed at the proxy. Modes: latency, bandwidth cap, drop every Nth packet, RST mid-stream, blackhole (accept, never forward), flap (up/down every N s). Plus an HTTP fault server for RSS, Torznab, update checks, URL adds and trackers: slow, huge, 500, truncated, wrong content type.
4. **OS-level scripts [O where noted].** `scripts/fault/*.ps1` and `*.sh`, each printing what it changes and how to revert it. They act only on paths under the scratch folder and `target/debug/corrent-data`.

## Risks

1. ~~**The lib/bin split (Z0) touches every module.**~~ Not needed (S9): every external-input parser is in a library crate.
2. **More vendoring means more upstream drift.** Prefer Corrent-side checks (E1, E2, E5) over patching unvendored crates. Each [V] patch (D5, F4, E2's peer-metadata check, D13 only if the token can't be passed from outside, FaultyStorage, F13) stays minimal, marked, and has an upstream diff. vendor-diff (E8) keeps it honest.
3. **The store schema v2 (D7) is a migration.** A bug there loses data. That is why D7 and the D6b rebuild that needs it are in S7, after S6: they ship only once the D9 file fixtures and the D8 kill test cover them, and the dated pre-migration backup stays. S2 ships only D6a, which needs no schema change.
4. **fsync costs on slow disks.** D4 adds fsyncs in S1. In the same milestone, store and `rss.json` saves move to the writer thread (F1 part 1), so the actor never waits on them. Settings saves stay on the UI thread until F2 (S3); D4 makes them no slower (the parent-dir fsync is Unix only, and `.bak` is refreshed less often). D5's fsyncs (S2) run inside librqbit's persistence flush; measure them in L4 and in the S8 slow-disk scenario, and debounce them in a patch only if the numbers demand it.
5. **Fault hooks leaking into release.** Prevented by `cfg` gating and the R7 binary scan.
6. **Flaky timing tests** erode trust in the bar. Use C5 (`tokio::time::pause`) and require 20 consecutive green runs.
7. **Tooling on Windows.** cargo-fuzz, sanitizers and miri are weaker on MSVC. The nightly Linux CI is the authority for fuzzing, so it depends on the owner pushing. Sanitizers and miri are optional and never gate a release.
8. **Owner-only scenarios** (admin VHD, adapter toggles, sleep/hibernate, power loss, `subst`, Linux/macOS, 72 h swarm soak) can block the bar. They are required once per engine-touching release cycle, not per commit, and Bar v1 doesn't need them.
9. **Watchdog false positives** during long rechecks or moves. Breadcrumbs mark these phases as expected, and the threshold only logs; it never kills.
10. **Diagnostics bundle privacy.** Use the O4 field allow-list over `Settings` (new fields excluded by default), tested; show the user the file list before saving.
11. **Suspected findings may be false** (D13 session surviving an engine panic, E1 path escape, E2 stack overflow, E4 unverified bytes, F11 hidden-window events, the UI-panic flush). Each starts with a failing test. If the test can't fail, drop the fix and record that.
12. **D14 forces full rechecks after every power loss.** On large libraries this can take hours. Limit it to torrents that were incomplete, show progress, and keep fast resume for complete torrents.
13. **D16 end-session handling is platform-specific.** Windows gives a short budget after `WM_ENDSESSION`. The flush comes first and the engine stop gets whatever time is left; the D14 recheck covers anything that didn't make it.
